# Campus Errand Grab：面向可量化 Impact 的继续优化方案

## 1. 文档目标

本文不以“继续堆功能”为目标，而是把后续工作组织为一条可验证的工程证据链：

```text
识别问题 -> 实施改动 -> 设计对照实验 -> 记录原始数据 -> 自动验收 -> 形成可追问的项目成果
```

所有数字分为两类：

- **已达成结果**：仓库中已有原始 JSON、自动化断言、测试报告或 CI 记录，可以用于项目介绍和简历。
- **下一轮目标**：尚未完成，仅用于定义验收标准；完成并复测前不能写成项目成果。

本文中的性能数据来自 Windows Docker Desktop、本地 Compose 环境和 Hikari 连接池大小 20 的受控实验。它们是指定场景下的容量观测，不代表生产 SLA、线上用户规模或通用系统上限。

截至 2026-09-12 的执行边界：W0 本地自动化验收为 `PASS`；W1 已完成 Redis 诊断 A/B，结论为未观察到稳定性能改善；W2 的本地安全回归为 `PASS`，但 Trivy 依赖/镜像扫描没有在本机运行；W3 的本地告警与时间线验证为 `PASS`，OpenTelemetry 和外部告警路由为 `NOT_RUN`；W4 的同机恢复演练为 `PASS`，但不覆盖 HA、跨主机或 PITR；W5 的本地支付沙箱回放为 `PASS`，不代表真实渠道接入；W6 尚未运行。总体验收见 `reports/runtime/current-workspace-validation.json`，工作包细节见 `docs/unfinished-impact-work-execution-plan.md`。

### 2.2 性能结论的正确边界

Redis 前置过滤的稳定价值是**减少数据库竞争压力**，不能泛化成“所有场景都提升吞吐并降低延迟”。正式矩阵中的中位数结果如下：

| 场景 | 开启 Redis RPS | 关闭 Redis RPS | RPS 变化 | 开启 Redis P99 | 关闭 Redis P99 | P99 变化 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 热点 500 | 380.03 | 351.95 | +7.98% | 1056.69 ms | 1142.41 ms | -7.50% |
| 热点 1000 | 333.84 | 361.69 | -7.70% | 2411.67 ms | 2233.99 ms | +7.95% |
| 多订单 1000×10 | 572.92 | 587.49 | -2.48% | 757.02 ms | 673.27 ms | +12.44% |
| 多订单 1000×20 | 642.60 | 587.65 | +9.35% | 665.12 ms | 728.61 ms | -8.71% |
| 多订单 1000×50 | 608.42 | 568.79 | +6.97% | 767.36 ms | 829.65 ms | -7.51% |

因此当前最有说服力的项目叙事是：

> 通过 Redis Lua 前置过滤与 MySQL CAS 最终裁决，在保持唯一赢家正确性的同时，将高竞争场景的数据库 CAS 压力减少 89.97%～99.90%；使用持续负载、Redis 故障注入和资金对账验证降级与恢复能力。

## 5. P0：定位并优化 Redis 路径的性能退化

### 已知问题

在热点 1000 和多订单 1000×10 场景，开启 Redis 后中位 RPS 分别下降 7.70% 和 2.48%，P99 分别上升 7.95% 和 12.44%。这说明 Redis 前置过滤降低了数据库 CAS 压力，但新增的网络往返、Lua 执行、连接等待或线程调度可能成为新瓶颈。证据：`reports/benchmarks/benchmark-report.md`。

### 做什么工作

1. 为 Redis Lua 增加调用次数、成功/失败、P50/P95/P99 延迟和连接池等待指标。
2. 同步采集 Hikari active/pending、数据库查询延迟、JVM GC pause、CPU、内存、线程池队列和容器资源。
3. 固定硬件、数据集、连接池和压测端，按 Redis 开/关各预热 1 次、正式运行至少 5 次。
4. 依次验证 Redis 连接池大小、超时、序列化、Lua 脚本内容和客户端并发模型，每次只改变一个变量。
5. 使用置信区间或至少报告 min/median/max；若差异落入波动范围，结论写为“无显著改善”。

### 如何量化

| 指标 | 当前基线 | 第一阶段目标 |
| --- | ---: | --- |
| 热点 1000 开启 Redis 的中位 RPS | 333.84 | 找到退化的主要等待项，并用指标证明其贡献 |
| 热点 1000 开启 Redis 的中位 P99 | 2411.67 ms | 优化后不劣于关闭 Redis 基线，或明确记录无法兼得的 trade-off |
| 多订单 1000×10 开启 Redis 的中位 P99 | 757.02 ms | 优化后不劣于关闭 Redis 基线，或证明差异属于实验波动 |
| 数据库 CAS 降幅 | 89.97%～99.90% | 优化过程中不得破坏该结果及唯一赢家约束 |

这里的目标不是预设“Redis 一定更快”，而是得到能够解释退化来源的受控 A/B 证据。

### 验收证据

- 新增 Redis、连接池、JVM 和容器资源指标的原始采样文件。
- 输出优化前后相同场景、相同次数的 A/B 报告。
- 自动断言单赢家、HTTP 5xx、数据库 CAS 和五项资金不变量。
- 对无改善或负向结果同样保留报告，禁止只选择最好的一次运行。

本轮已实现观测基础：Java 侧记录 Redis Lua 调用/成功/失败及 P50/P95/P99 Timer、MySQL DB CAS Timer；`scripts/load_test.py` 将 Hikari、JVM、线程池、CPU/内存和 Docker 容器资源的白名单采样写入每个原始 JSON，并由 `scripts/generate_runtime_benchmark_report.py` 生成独立诊断报告。证据：`reports/benchmarks/runtime-bottleneck-report.md`。

诊断 A/B 已按热点 1000 和多订单 1000×10 各完成 Redis 开/关 1 次预热、5 次正式运行。热点 1000 中 Redis 开启相对关闭的中位 RPS 为 150.78 vs 148.90、P99 为 1910.75 ms vs 2028.27 ms；Redis Lua 过滤 P99 为 22.00 ms，Hikari pending 峰值为 3。多订单 1000×10 中位 RPS 为 535.20 vs 542.55、P99 为 615.98 ms vs 621.18 ms；Redis Lua 过滤 P99 为 1.30 ms，Hikari pending 峰值为 0。两组均保持 HTTP 5xx 为 0、5/5 轮对账通过、单赢家断言通过；这些结果定位了 Redis Lua、DB CAS 和连接池等待的候选观测项，但未证明已完成性能优化。证据：`reports/benchmarks/runtime-bottleneck-report.md`、`reports/benchmarks/raw/run-index-20260912-114727-770519.json`、`reports/benchmarks/raw/run-index-20260912-120117-901973.json`。

当前 W1 验收结论为 `PARTIAL`：报告已保留 min/median/max/stdev、失败样本和正确性断言，但尚未完成 Redis 客户端连接池 active/idle/pending 指标、单变量参数实验和最佳配置复跑。因此不能把本轮 A/B 结果写成 Redis 性能优化完成。

### 完成后可写的结果模板

## 9. P2：支付、退款与通知业务闭环

### 做什么工作

1. 接入支付沙箱，完成充值、回调验签、重复回调和乱序回调处理。
2. 增加订单取消、退款、结算失败和人工补偿状态机。
3. 将支付回调、账本入账、通知事件纳入幂等键、Outbox 和审计链路。
4. 增加争议单与管理员处理记录，明确权限和资金冻结边界。
5. 对重复、乱序、超时和部分失败执行批量回放。

### 如何量化

| 指标 | 验收目标 |
| --- | ---: |
| 同一支付回调重复回放 | 建议至少 1,000 次，仅产生 1 次有效入账 |
| 退款请求重复回放 | 建议至少 1,000 次，仅产生 1 次有效退款 |
| 乱序事件最终一致率 | 100% 达到预期终态 |
| 通知重复发送率 | 0 |
| 资金对账异常数 | 0 |
| 人工补偿可审计率 | 100% 包含操作者、原因、前后状态和 traceId |

“1,000 次”是建议验收规模，不是当前已经完成的结果。

本轮已在本地 SANDBOX 对支付回调和退款分别执行 1,000 次重复回放，并验证签名错误、过期时间戳、参数冲突、乱序回调、通知唯一性、补偿审计和资金对账。结果见 `reports/payment/payment-validation-report.md` 和 `reports/payment/payment-replay-report.json`。该证据不覆盖真实支付渠道、渠道超时或外部通知网络故障，因此 W5 仍为 `PARTIAL`。

### 验收证据

- 支付沙箱回执、脱敏回调样本、回放脚本和机器可读结果。
- 重复回调前后的订单、账本、Outbox 与通知记录差值。
- 失败补偿和人工处理的审计记录。

### 完成后可写的结果模板

## 10. P2：接近生产的容量验证

### 做什么工作

1. 将压测端与被测服务部署到不同主机，避免本机资源竞争污染结果。
2. 固定 CPU、内存、数据库规格、网络和 JVM 参数，记录环境清单。
3. 同时覆盖热点、混合业务、持续负载和阶梯增压，寻找稳定容量与拐点。
4. 至少重复 5 次，报告中位数、范围和资源饱和点。
5. 将结果命名为“预生产容量基线”；只有真实部署并长期观测后，才能形成生产 SLA。

### 如何量化

| 指标 | 记录要求 |
| --- | --- |
| 最大稳定 RPS | 同时满足既定错误率、P99 和对账约束的最大档位 |
| P50/P95/P99 | 按场景和负载档位分别记录 |
| 资源利用率 | 应用、MySQL、Redis 的 CPU、内存、连接与 IO |
| 饱和点 | 记录首个违反 SLO 的档位及对应瓶颈 |
| 30～60 分钟稳定性 | HTTP 5xx、GC、连接等待、Outbox 积压和对账结果 |

### 验收证据

- 基础设施规格、启动参数、压测脚本版本和完整原始结果。
- 自动生成的容量曲线与瓶颈分析。
- 失败档位保留在报告中，不只展示最佳数字。

### 完成后可写的结果模板

> 在固定【CPU/内存/数据库】规格和独立压测机环境下建立容量基线，在 P99≤【阈值】、HTTP 5xx≤【阈值】及资金对账异常为 0 的约束下，稳定处理【RPS】并定位系统饱和点为【瓶颈】。

## 13. 禁止或暂缓使用的表述

- 不写“生产支持 300/400/600+ RPS”：当前是本地 Docker 场景数据，不是生产容量。
- 不写“Redis 让吞吐翻倍”或“所有场景性能均提升”：正式矩阵存在负向结果。
- 不写“系统 100% 可用”或“达到生产级”：尚未完成真实 HA、跨主机/PITR、OpenTelemetry、外部告警路由和长期运行验证。
- 不写“避免线上资金损失”：没有真实线上事故、损失基线或业务数据。
- 不写“零故障”：可以写指定实验中 HTTP 5xx 为 0，但不能外推到全部故障和全部运行时间。
- 不把未来验收目标、建议回放次数或设计阈值写成已达成结果。

## 14. 完成定义

每个优化工作包只有同时满足以下条件，才可以转化为正式项目成果：

1. 改动已实现，并通过功能、异常与回归测试。
2. 对照环境和指标口径固定，至少保留基线与优化后的完整数据。
3. 原始结果、报告生成方式和失败样本可追溯。
4. 正确性不变量、系统错误率和性能指标同时验收，不能只看 RPS。
5. 结论明确适用场景、测试环境和个人责任边界。
6. README、项目简历、交接文档与最新证据保持一致。

做到这一步，项目的含金量不再依赖功能数量，而来自可证明的工程决策、故障边界、量化结果和复现能力。
