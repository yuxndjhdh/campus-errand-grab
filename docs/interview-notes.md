# Interview Notes

## Redis 放过了但 DB 拒了怎么办？

Redis 是过滤器，不是权威。已消费 marker 直接返回统一冲突，避免热点失败请求继续读库；marker 缺失、超时或 Redis 不可用时回退到数据库 CAS。数据库影响行数为 0 仍是最终判据，Outbox 和重建任务负责恢复索引，不会出现两个赢家。

## 结算重试两次怎么办？

同一个订单使用 `SETTLE:ORDER:{id}` 作为主键，插入幂等键、账户变化和订单状态在同一个事务中。事务回滚时幂等键也回滚；事务提交后重试撞主键直接 no-op。状态 CAS 和分录唯一键提供额外兜底。

## Outbox 事件重复投递怎么办？

事件唯一键限制同一业务事件只写一次，Worker 的 Redis `SET`、`ZADD` 和删除操作都可重复执行。事件处理状态、重试次数和最后错误保存在数据库，超过上限进入 `DEAD` 并可通过查询结果告警。

## 同一个充值幂等键换了金额怎么办？

幂等表保存规范化的用户 ID、金额和 SHA-256 指纹。相同 key、相同指纹是重放；指纹不同返回 `409 IDEMPOTENCY_CONFLICT`，不会修改余额或追加账本。

## 哪一分钱可能漏掉？

没有浮点数。佣金取整后只计算一次，跑腿人金额用 reward - commission 得到。每个业务的分录数量和符号固定，INV-1 每次对账验证全局和为零。

## 资金永久冻结怎么办？

截止时间存订单行，不依赖 Redis。ZSet 提供及时性，数据库索引扫描提供完备性，启动扫描覆盖宕机窗口。INV-3 检查托管池与未终态订单总额，INV-5 检查已过期未终态订单。

## 两个线程都通过过滤器为什么不会坏？

它们最终在同一条 InnoDB 订单行上串行执行。第一个提交 TAKEN 后，第二个重新评估 `status='PUBLISHED' AND taker_id IS NULL`，影响行数为 0。过滤器允许多少流量与谁赢是两个不同问题。
