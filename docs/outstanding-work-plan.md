## 3. P0：修正压测指标口径（已完成）

### 3.1 问题

历史版本中 `mixed` 和 `sustained` 场景没有采集完整指标，报告生成器也可能把缺失字段误读为 0。

### 3.2 实施方案

1. 在 `mixed()` 和 `sustained()` 开始请求前调用管理员统计接口，记录：
   `grabDbCas`、`redisFiltered`、`rateLimited`、`grabAttempts` 和 `grabWinners`。
2. 请求完成后再次采集，写入 `*Delta` 字段。
3. 在报告生成器中区分三种状态：真实数值、字段未采集、采集请求失败；禁止把缺失值静默转换为 0。
4. 为每个场景增加“指标采集完整性”字段，只有完整采集时才允许生成数据库压力结论。
5. 重新运行多订单和持续负载场景，保留新的原始 JSON，并重新生成表格和图表。

### 3.3 验收标准

- 每个正式压测 JSON 都包含完整的指标增量或明确的 `metricsUnavailable` 原因。
- 多订单场景的 DB CAS、Redis 过滤、限流和赢家指标可追溯到原始 JSON。
- 报告不再将缺失指标写成 0，也不使用未采集指标推导过滤率。
- 重新生成的图表与原始 JSON 数值一致。
- 现有单赢家断言、HTTP 系统错误率和五项对账结果保持通过。

## 6. P1：生产安全加固

### 6.1 必须处理的问题

- `/actuator/prometheus` 不应默认暴露在公网入口。
- `JWT_SECRET` 仍有开发默认值，生产启动时必须强制提供高熵密钥。
- 当前 JWT 为自实现 HMAC 解析逻辑，需要补充安全边界测试或迁移到成熟库。
- 登录接口缺少失败限流、审计和异常账号保护。
- 管理接口需要网络隔离、反向代理访问控制或额外认证层。

### 6.2 实施方案

1. 将 Actuator 管理端点迁移到内部端口或只允许监控网段访问。
2. 生产 profile 禁止 JWT 和数据库密码使用默认值，启动时校验配置并快速失败。
3. 引入密钥管理服务或云 Secret Manager，设计密钥轮换和旧密钥过渡窗口。
4. 为登录、注册、充值和管理接口增加 IP/账号维度限流、审计日志和告警。
5. 对 JWT 增加签名算法固定、时钟偏差、过期、密钥轮换和异常 Claim 测试。
6. 使用 TLS、最小权限数据库账户和脱敏日志；禁止日志记录密码、完整 JWT 和支付敏感信息。

### 6.3 验收标准

- 生产配置缺少密钥时应用不能启动。
- 公网请求无法访问 Prometheus 和管理端点。
- 密钥轮换期间旧 token 的行为有明确测试和文档。
- 登录暴力尝试能被限流并产生审计事件。
- 安全回归测试在 CI 中通过。

## 7. P1：生产高可用与灾备

### 7.1 数据库

1. 使用云 MySQL 或主从架构，明确故障切换方式。
2. 配置自动备份、binlog/PITR 和备份加密。
3. 演练“误删余额”“数据库实例故障”“迁移失败”三类恢复流程。
4. 记录 RPO、RTO、连接池上限、锁等待和慢查询阈值。

### 7.2 Redis

1. 使用托管 Redis、Sentinel 或 Cluster，明确故障转移时间。
2. 保留当前 MySQL CAS 降级和启动重建机制。
3. 限制恢复重建的并发度，防止 Redis 恢复时把压力集中打到数据库。
4. 演练 Redis 数据丢失、主从切换、网络分区和恢复后的数据重建。

### 7.3 验收标准

- 数据库和 Redis 故障切换有脚本、时间记录和结果报告。
- 恢复后订单状态、延迟索引、Outbox 和五项资金不变量一致。
- RTO/RPO 有实测值，而不是设计目标值。
- 备份能够在独立环境恢复并完成冒烟流程。

## 8. P2：业务生产化范围

不要为了增加接口数量而扩大范围，先定义可上线 MVP：

### MVP 必需项

- 真实支付充值和回调验签。
- 退款、取消、结算失败和人工补偿流程。
- 订单分页、查询和基础管理操作。
- 用户通知和关键状态变更消息。
- 订单争议、申诉和管理员处理记录。
- 操作审计、隐私脱敏和数据保留策略。

### 第二阶段能力

- 风控规则和异常抢单检测。
- 位置、配送轨迹和跑腿人匹配。
- 评价、信用分和纠纷仲裁。
- 多校区或多租户隔离。

### 验收标准

- 每个 MVP 流程都有状态机、权限、幂等、失败补偿和审计设计。
- 外部支付回调可重放且不会重复入账。
- 业务数据的保留、删除和脱敏规则得到实现和测试。

## 9. P2：质量门禁与生产运维

### 实施方案

1. 在 JaCoCo 中增加最低指令和分支覆盖率门禁，阈值应按当前基线逐步提高。
2. 增加依赖漏洞扫描、Secret 扫描和容器镜像扫描。
3. 引入结构化日志、traceId、OpenTelemetry 链路追踪和错误分类。
4. 为抢单、结算、Outbox 和对账定义 SLI/SLO：成功率、延迟、积压、恢复时间。
5. 将 Grafana 告警接入通知渠道，并为告警补充值班手册和处理时限。
6. 将冒烟、故障演示和压测报告生成加入可选的发布流水线，而不是依赖人工记忆。

### 验收标准

- 新增代码导致覆盖率低于门禁时 CI 失败。
- 高危依赖或泄露凭据时 CI 失败。
- 任一请求可以通过 traceId 关联 HTTP、数据库、Redis 和 Outbox 日志。
- 每个核心告警都有负责人、排查步骤和恢复验证。
